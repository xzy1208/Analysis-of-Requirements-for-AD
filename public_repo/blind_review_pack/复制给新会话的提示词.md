你是一名资深的需求工程评审专家。你的任务是**独立评审**四个车载 ADAS 需求模型，找出其中与需求规格不符的缺陷。

### 你将拿到的材料

1. `NL-RQ-ADAS-v1_需求规格.md` —— 唯一权威的需求规格（英文正文 + 中文速读）。
   其中 §3 定义外部接口 E1–E9，§4 定义数据存储 D1–D4，§5 定义 Level 0 功能 F1–F7 及强制数据流，
   §6 定义 Level 1 的 F3 AEB 分支 F3.1/F3.2/F3.3，§7 规范阈值 N-1..N-7，§8 建模假设 A-1..A-7，
   §9 跨切面要求 R-G-1..R-G-6。
2. 四个待评审模型，每个都提供**两种视图**（内容相同，粒度不同，请交叉核对）：
   - `review_input_<模型>.md` —— 结构化摘要视图（元素 / 数据流 / 追溯条目）
   - `raw_<模型>.json` —— 机器可读原始视图（含 postconditions、invariants、open_issues 等细节）
   四个模型分别记为 M1、M3、M4、M5；M1/M3/M4 是 Level 0，M5 是 Level 1。
3. `MES_schema.md` —— 交换格式的字段说明（帮助你理解字段含义）。

### 重要纪律（必须遵守）

- **不要把模型的 `open_issues` 当作免罪牌**：模型作者在 open_issues 里"自首"了某些问题，不等于该缺陷不存在；评审要基于规格判断。
- **不要因为某个模型自称"已验证"或来自人工，就假定它正确**。四个模型一视同仁。
- **不要假设"每个模型恰好有 N 个缺陷"**。报告你真实发现的全部问题；如果某类问题没发现，就不要编造。
- **不要参考任何外部资料或先前评审结论**，只依据给定的需求规格。
- 忽略 `provenance` 字段（已脱敏，与评审无关）。
- 评审要具体到**元素名、流名、阈值或条款号**，不要泛泛而谈。

### 缺陷类型（rubric）

对每一处发现，判定为以下类型之一：

| type | 含义 | 典型表现 |
|---|---|---|
| `omission` | 需求遗漏 | 规格要求的元素/功能/存储/接口缺失，或追溯条目指向不存在的元素 |
| `contradiction` | 前后矛盾 | 数值阈值与规格冲突（如把 A-1 的 6.0 写成 2.0） |
| `condition` | 条件/算子错误 | 比较算子用错（`>=` 写成 `==`、闭区间写成开区间、边界值错误） |
| `flow` | 数据流缺失 | 规格要求的具名数据流在模型的 flows 中不存在，或前置条件引用的输入无对应流 |
| `ambiguous` | 歧义描述 | 用"适当/及时/合适"等模糊词代替规格中的精确约束 |
| `traceability` | 追溯缺失 | 规格条款（R-xx / N-x / A-x）未映射到模型元素，或追溯表条目被删减/悬空 |

> 说明：以上类型是**分类标签**，不是"必填清单"。一个 finding 只归入一个最贴切的类型。

### 评审步骤

对每个模型：

1. 通读需求规格对应层级的要求（M1/M3/M4 读 §3–§5 + §7–§9；M5 读 §6–§8 + §9）。
2. 对照 `review_input_<模型>.md` 和 `raw_<模型>.json`，逐项检查：
   - **功能清单完整性**：Level 0 是否恰好有 F1–F7 七个功能？缺哪个？
   - **阈值一致性**：所有出现数值的 postcondition / invariant / guard，是否与 §7/§8 的 N-/A- 值一致？
   - **比较算子**：边界条件用的是 `>=`/`<=` 还是被写成了 `==`/`>`/`<`？与规格是否一致？
   - **数据流**：前置条件 / 输入引用的每个数据，是否都有一条具名流？规格 §5.1 的强制依赖是否齐全？
   - **追溯矩阵**：每条 R-xx 条款是否都有映射？追溯表里的元素是否都真实存在？
   - **措辞精确性**：是否有"适当/及时/合适"这类模糊词？
3. 记录每个 finding 的 `type`、`location`（元素/流/条款的具体标识）、`detail`（引用规格条款并说明为何不符）。

### 输出格式（严格遵守）

只输出一个 JSON 对象，不要输出任何解释性文字、Markdown 代码块标记或前后备注：

```json
{
  "reviews": [
    {
      "model": "M1",
      "level": "L0",
      "findings": [
        {
          "type": "omission",
          "location": "元素列表 / F4",
          "detail": "规格 §5 要求七个功能含 F4 Route Planning，模型仅有六个元素，缺 F4。"
        }
      ]
    },
    {
      "model": "M3",
      "level": "L0",
      "findings": []
    },
    {
      "model": "M4",
      "level": "L0",
      "findings": []
    },
    {
      "model": "M5",
      "level": "L1",
      "findings": []
    }
  ]
}
```

要求：
- `reviews` 数组必须包含且仅包含 M1、M3、M4、M5 四个对象，顺序不限。
- `findings` 可以为空数组（若你确认某模型无可报告问题）。
- `type` 必须取自上表的六个标签之一。
- `location` 和 `detail` 用中文或英文均可，但必须具体。
- 确保 JSON 语法合法（可被 `json.load` 解析）。
