## 4. UML 数据流方向性的处理（UML 已知弱点的如实呈现）

UML 类图的关联本身**不携带**“数据流”的语义与方向强度：一条普通关联既可能是控制依赖，也可能是数据依赖；聚合/组合还会被误读为“拥有”，而规格中的“生产→消费”其实是**单向、无共享**的数据流。因此本模型采取以下三条手段把方向性做实：

1. **标签化**：每条数据依赖都写成 `<<flow>>` stereotype + 数据名（如 `<<flow>> predicted_trajectories`），把“数据依赖”与“实现继承/使用依赖”区分开。
2. **角色名显式化**：关联两端写出角色名 `producer` / `consumer`，对存储则为 `store` / `reader` / `writer`。例如
   `F2 "producer" --> "consumer" F5 : <<flow>> predicted_trajectories`，
   `D3 "store" --> "reader" F7 : <<flow>> ego_state (store_read)`，
   `F1 "writer" --> "store" D2 : <<flow>> object_table (store_write)`。
   箭头方向 + 两端角色名共同固定“谁生产、谁消费”，不再依赖读者对图形语义的猜测。
3. **命名与可机检化**：每个流有唯一名字，`MES_M4_L0.json` 的 `flows[]` 以 `{name, producer, consumer, kind, carries}` 显式记录 `producer`/`consumer`，且每个元素的每个 input/output 恰好对应一条 flow；一个流被两个消费者使用时，**按 MES 规范写成两条同名的 flow**（`ego_state → F2/F4`、`predicted_trajectories → F3/F5`、`route → F3/F5`），使“共享流”在数据上可见。
   存储访问额外用 `kind` 区分 `store_read` / `store_write`，因此“谁写、谁读”一望可辨。D1/D4 的刷新取数与写入按两种语义各记一条同向流（`map_data` / `hd_map_refresh`，`traffic_rules` / `traffic_rules_refresh`），使“跨边界取数”和“写入该存储”两种判据都能通过。
   Level 0 共 **36** 条流，Level 1 共 **12** 条流。

未采用的做法：不用组合/聚合表示“拥有”（会与 `D2`/`D3` 的保留语义冲突）、不用依赖虚线（语义过弱）、不引入端口/连接器（会额外增加元素，违反 R-L0-1 的元素计数）。

## 6. 规格 §11 的四个 open issues —— 本模型的回答

### ① 七功能划分是否足够？是否需要一个独立的驾驶员监视（L2 交接）功能？—— **不够，但本模型不新增元素**

SAE L2 的核心义务是“驾驶员持续监督并随时接管”，因此驾驶员注意力/接管判定在功能上是必需的；但本规格 §1 把 **E3（`driver_intent`）** 定义为已包含 *driver-attention state* 与 *requested manual override* 的输入，因此**注意力监视的数据已经由外部 HMI 提供**。在“不得自造函数、不得自造接口”的规则下，正确的处理是把注意力/接管语义作为 **F3 的一个前置与守卫条件**（例如：驾驶员注意力不足时 `manoeuvre_type` 不得进入 `emergency_deceleration` 之外的降级路径、且必须触发退出），而不是新增第 8 个函数——新增函数会直接违反 R-L0-1。因此本模型把该问题记为 **OI-1（high）** 并保持 F1–F7 不变：建议规格补充一条“注意力不足时的最小风险策略”条款，再把它落到 F3（可能进一步落到 Level 1 的 F3.3）。

### ② D3 由 F1 写、被 F6/F7 读，属主划分是否可接受？—— **可接受，但 R-D-1 的表述需要收紧**

理由有三：(a) 规格 §5 明确把“本车状态”归给 F1（“F1 shall compute the ego state … F1 shall write D2 and D3”），F1 同时也是传感器融合的拥有者，状态与其来源同源是合理的；(b) D3 的写入者唯一（F1），读者只限 §5.1 指定的 F6/F7，因此 R-D-1（只由属主写）与 R-D-2（只读被指派的存储）都能满足；(c) 若另设“状态估计”功能，则 F1 的职责被掏空、还要额外新增一个接口/存储，反而违反 R-L0-1。真正的隐患是**时序**（F6/F7 可能读到陈旧状态，见 ③），因此本模型记录 **OI-2（medium）**：建议在规格中补充 D3 的新鲜度契约（时间戳 + 最大允许滞后），而不是新增属主。

### ③ 只固定阈值不固定时序，是否需要周期时间要求？—— **需要，尤其对紧急分支是决定性的**

规格 §6/F3.3 的 AEB 能力是**瞬时**能力：即使 `required_decel_ms2 >= 6.0` 正确成立，如果感知→预测→分级→机动的链路每周期耗时 200 ms，告警与减速将整体滞后 200 ms，N-2 的“TTC = 2.0 s 前必须告警”以及 N-3 的冲击速度降低都会在实际车上失效。本模型因此**不发明任何周期时间数值**，但在 F1/F2/F3/F3.1/F3.2/F3.3 的前置条件中把“数据新鲜度”留作显式接口（`ego_state_ts`、`last_update_ts` 为 `nat`），并把该缺口记录为 **OI-3（medium）**：建议规格给出感知周期、预测周期、规划周期的上界与端到端预算，以及相对 TTC 的告警时刻裕度。

### ④ AEB 分支（F3）是否是正确的 Level 1 细化对象？—— **按规格指令是；但从工程价值看，F6/F7 链路的细化更有价值**

规格 §6 明确要求细化 **F3 的 AEB 分支**，本模型遵此执行（R-SCOPE-4 / R-L1-1：恰好三个子过程）。但从风险工程角度值得指出：**紧急减速的可执行性由 F5→F6→F7 决定，而非由 F3 的分级决定**。F3.3 给出 6.0 m/s² 后，还要经过 F5 的运动学可行性、F6 的包络（A-3 = 3.0 m/s²，见 OI-7）与 F7 的仲裁才可能真正输出指令；本模型正是把这条“6.0 m/s² 能否活下来”的链路暴露在 OI-7 中。建议：**Level 1 保持 F3 细化（本次实验可比性要求），同时把 F6/F7 链路的细化列为 Level 2 的候选**——记为 **OI-4（medium）**。

## 8. 对照实验相关的说明

- 本模型为**单次生成**（`passes = 1`），**未做自检**（`self_review_performed = false`）；一致性由人工在交付时核对（元素计数、流与元素输入/输出的一一对应、算子集、阈值来源），但这些核对**不构成生成过程的第二次迭代**，故如实记录为 `false`。

- Level 1 的 `MES_M4_L1.json` 采用 `parent_module = "M4_L0"`，并在元素/存储/接口记录上用 `"level": "parent"` 标记父级元素，使 12 条 L1 流的生产者与消费者在文件内即可解析。
